# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A local collection of Claude Code plugins, one per top-level folder. `.claude-plugin/marketplace.json` publishes them as the marketplace `kwcantrell-plugins` (GitHub `kwcantrell/kwcantrell-plugins`, public).

| Folder | Kind | How it is loaded here |
| --- | --- | --- |
| `factory/` | Classic plugin: skills, agents, a command hook, a Python CLI | Marketplace (`factory@kwcantrell-plugins`) |
| `usage-dashboard/` | Mod (TSX hooks module) plus Python scripts and skills | Marketplace (`usage-dashboard@kwcantrell-plugins`) |
| `context-explorer/` | Mod (TSX hooks module) only | Listed in the marketplace, but loaded here through `CLAUDE_CODE_PLUGIN_DIRS` in `~/.claude/settings.json` so edits hot-reload |

A new plugin needs an entry in `marketplace.json` (or a plugin-dir entry) to load at all.

## Commands

```sh
claude plugin validate <plugin-folder>   # manifest + hooks module: what it hooks, calls, adds to $
claude plugin test <mod-folder>          # runs every *.test.ts(x) under the folder; exits 1 on failure
tsc -p <mod-folder>                      # typecheck a mod
```

There is no per-test filter: to run one test file, point `claude plugin test` at a folder containing just that file, or run the whole mod (they are small). There is no package.json, build step or linter; everything ships as source.

Python scripts are stdlib only and are always run isolated: `python3 -I <script> ...`. Each script's module docstring is its usage line. Notable:

- `python3 -I usage-dashboard/scripts/serve_dashboard.py [port]` serves the live dashboard (default 8788, binds 127.0.0.1).
- `python3 -I usage-dashboard/scripts/events.py {emit|backfill|aggregate} <dir> ...` is the event store the mod and the server share.
- `factory/bin/factory --help` lists every factory CLI command; `factory status` and `factory stats` are read-only.

## Mods (usage-dashboard, context-explorer)

- `hooks/hooks.json` is `{ "modules": ["./register.tsx"] }`; `hooks/register.tsx` is the whole mod and imports from `'claude-code'`. Tests sit beside it (`*.test.tsx`) and import from `'claude-code/testing'`, seeding atom state by key and shape tag.
- `.claude-plugin/types/` is generated by Claude Code on every load (API typings and the `tsconfig.json` the mod's own `tsconfig.json` extends). Never edit it; it is regenerated.
- `types/index.d.ts` holds the mod's own data shapes, referenced from `plugin.json` `"types"`.
- Persisted state uses `atom(...)` with a `shape` tag. Bump the tag (e.g. `turns-1` -> `turns-2`) whenever that value's fields change, so old stored values read as absent instead of the wrong shape.
- The plugin-authoring skill is the reference for the mod API (`$`, events, elements); load it before changing a mod.

## usage-dashboard data flow

1. The mod (`register.tsx`) appends one JSON event per turn/skill/session via `$.process.run(['python3','-I', scripts/events.py, 'emit', <dir>])` into `~/.claude/usage-events/<session-id>.jsonl` (one file per session, so sessions never contend).
2. `events.py backfill` rebuilds events for sessions that ran without the mod from `~/.claude/projects/**` transcripts; `aggregate` summarizes.
3. `export_dashboard.py` reshapes the aggregate into flat tables; `serve_dashboard.py` serves those plus `bash_commands.py`, `timing.py` and `patterns.py` as `/api/*` to `web/index.html`.
4. Transcript parsers cache files by (mtime, size); keep that when changing them.

`scripts/test-time/` is a separate analysis of how long agents spend on tests/checks (`run.sh` drives `checks.py`, `bench.py`, `build_analysis.py`).

## factory

Read `factory/README.md` for the pipeline (intake -> build -> proof -> review -> ship -> done) and its design rationale. Key points when changing it:

- `factory/bin/factory` (single Python file) is the state machine and the only writer of `job.json`. Gates live there, not in prompts: exit 1 = refused, 2 = escalated to a human.
- Station prompts: `skills/run/SKILL.md` (supervisor), `agents/*.md` (builder, verifier, three reviewers). `skills/approve` and `skills/ship` are human-only.
- `scripts/human-gate.sh` (a `PreToolUse` Bash hook) turns `factory merge|approve|rework` into a permission prompt. A new human-only command must be added there too.
- `dashboard/index.html` is one dependency-free file that polls `jobs/*/job.json` through a plain directory-listing server. Fields added to `job.json` need handling there.
- Runtime state goes in the *target* project's `factory/` dir (`jobs/`, `worktrees/`); this repo's `factory/` folder is the plugin source, not runtime state.
- Optional per-project config is `factory.json`; the CLI refuses unknown keys, so new settings must be added to `DEFAULTS` and validation.
